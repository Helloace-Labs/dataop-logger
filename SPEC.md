# Aftershock logger: design spec (v0.4)

The logger is published as the `aftershock-logger` package (Python package `aftershock_logger`), renamed from `dataop-logger`. The old names stay as aliases: `import dataop_logger` returns the same modules, and the `dataop-logger` command is still installed next to `aftershock-logger`. On-disk names do not change in v1: the `dataop/` sidecar folder, the reader's `dataop.*` columns, `dataop_export.json` and the manifest key `env.software.dataop_logger` are read and written as before, so existing datasets keep working. Any later folder rename will keep reading `dataop/`.

## What the logger is in Aftershock

The logger is the part of Aftershock that runs on the robot's computer, inside the control loop. It is a small open-source Python library. On every frame it records what post-training needs and a normal LeRobot recording drops: who drove (the policy, a human on the leader arm, or a rescue skill), what the policy proposed, what the expert did, the command actually sent, timing, and how the run ended. It writes these into a sidecar folder next to the LeRobot dataset and never changes the dataset itself, so the dataset still loads and trains anywhere.

Everything else in Aftershock reads what the logger wrote: Review shows it and stores labels next to it, Train builds training sets from it, Results scores it, and the agent works on it. The logger is how data gets into Aftershock, in three ways:

| How runs are recorded | Who drives the robot | Where the logger runs |
| --- | --- | --- |
| Drive mode | Aftershock's station app | Inside our station app; the user installs nothing else |
| Watch mode | The customer's own software | Inside the customer's control loop, added in a few lines by them or their agent |
| Import | Already recorded, no logger | Not at all; `import` fills the same sidecar from existing files, and fields it cannot know stay `unknown` |

The same package also ships a local viewer (`aftershock-logger view`), which is the offline version of Review, and the export command that builds training sets.
## Purpose

A small open-source Python package that records the provenance post-training needs alongside a normal LeRobot recording, without changing the LeRobot dataset. Most stacks record what the robot did. They drop what the base policy proposed, what the expert would have done, who was in control, how long each step took, and how each run ended. Those are what DAgger and residual-network datasets need, and they are hard to recover later.

v0 claims: **DAgger and supervised residual datasets**, plus **RL-ready transitions** when the user supplies per-tick reward. It does not claim residual RL datasets from episode outcomes alone.

## Users and first test setups

- Teams running a LeRobot policy (ACT, SmolVLA, pi0.5) on a real arm, with a human or a scripted skill sometimes taking over or blending in.
- First setups: our SO-101 tube pick (SmolVLA, rescue skill, base policy kept running in shadow during rescues) and a second low-cost arm doing cup stacking (ACT or SmolVLA, camera-guided skill).

## Core model

- **Run:** one LeRobot episode attempt. Gets a `run_id` (UUID4) at `start_run`, never reused.
- **Tick:** one LeRobot frame. `dataset.add_frame` returns nothing, so the logger is the exclusive add path during a run: it requires `dataset.has_pending_frames() == False` at run start, calls `dataset.add_frame` first, and assigns the sidecar `frame_index` from its own successful-add counter starting at 0. Before save it checks that counter against the episode buffer size through a small, version-tested adapter (the only place private LeRobot state is touched). Post-save validation is authoritative.
- **Prediction:** one policy inference. Chunked policies produce an action chunk that several ticks draw from.

## Per-run action schema

Declared once per run, stored in the run manifest, checked on every tick:

`action_schema = {names[n], units[n], space: "joint_position" | "joint_velocity" | "ee_delta" | "custom:<name>", frame, bounds: {low[n], high[n]} or null (descriptive, not enforced), dtype, rate_hz, normalization_note}`

Values are always logged denormalized, in robot command space. `id` is the SHA-256 of the schema's canonical JSON (sorted keys, no whitespace), derived by the logger, never supplied by the caller.

`base_action`, `expert_action` and `sent_action` must all be in this space, the robot command space, before they reach the logger. Policy-space outputs are converted by the user's postprocessor first. A shape mismatch raises immediately. A run may use a different schema from other runs; files are per run, so shapes never mix in one table.

## Per-tick table: `dataop/runs/<run_id>/ticks.parquet`

| Field | Type | Meaning |
| --- | --- | --- |
| `frame_index` | int64 | Exact index assigned by LeRobot in this episode |
| `control_mode` | enum | `base`, `expert`, `blend`, `none` |
| `expert_source` | string or null | `human`, `skill`, or a namespaced string such as `skill:rescue_v3` |
| `blend_weight` | float32 | Expert weight in `[0,1]` when `blend`, else 0 or 1 |
| `base_action` | float32[n] | Base policy's selected action for this tick, before safety filters |
| `base_valid` | bool | False when the base policy did not run this tick |
| `expert_action` | float32[n] | Expert's action, even when not executed |
| `expert_valid` | bool | False when no expert label exists |
| `sent_action` | float32[n] | Final command after arbitration and all software safety transforms, as passed to the robot API. The logger coerces it once to the schema dtype and passes that same array into the LeRobot frame, so the two are byte-identical |
| `safety_modified` | bool | True when a clip, rate limit or guard changed the command |
| `inference_id` | int64 or -1 | Prediction that produced `base_action` |
| `chunk_offset` | int32 or -1 | Step within that prediction's chunk |
| `prompt` | string | The text the policy received on this frame (any string, empty included), or `unknown`. A prompt that changes during a run means a planner is present; the distinct prompts are its subtasks and the changes are its boundaries. So with `planner` null the known prompt never changes within a run |
| `prompt_rev` | int64, -1 when unknown | Counts prompt changes. Never goes down within a run; ticks with the same known `prompt_rev` carry the same known prompt |
| `subtask_cmd` | string or null | The subtask id the planner commanded on this frame; null when no planner commanded one; `unknown` when not recorded (also the default when the planner is null). Never a subtask id when the manifest's `planner` is null |
| `control_gen` | int64, -1 when unknown | The command generation counter of the control loop (it increments at a takeover, a stop or a fault). Never goes down within a run |
| `obs_ns` | int64 | Required. Monotonic time the complete observation bundle used for this action became available. `clock.obs_timestamp_kind` says whether it is a capture time or a bundle-completion time. Per-camera alignment is out of scope in v0 |
| `sent_ns` | int64 | Required. Monotonic time the command was sent |
| `obs_skew_ns` | int64 or -1 | Optional: max minus min camera time in the bundle, when known |
| `reward` | float32 | User-supplied reward for applying `sent_action` at this tick; `reward_valid` false when absent |
| `reward_valid` | bool | |
| `terminated` | bool | True only on the last tick of a run that reached a true terminal state |
| `truncated` | bool | True only on the last tick of a run cut off (timeout, abort) |

Arrays are fixed-size with explicit validity flags, never null lists. NaN is not used as "missing".

`prompt`, `prompt_rev`, `subtask_cmd` and `control_gen` (logger task L2) are written by every run from this version on, and are all present or all absent. A ticks file from an older logger has none of them, and every tick reads as unknown; `validate` accepts both. `validate` also reports a manifest whose policy reads as null (no policy ran, by the legacy rule above) while a tick carries a `base_action` or is driven by the policy. The two counters are int64 on disk with -1 for unknown, and the training reader keeps -1 there (like `inference_id`). `reader.tick_records(run_path)` gives each tick in the schema's record form, with the literal `unknown` for an unknown counter and for every L2 field of an older run.

**Transition convention.** Row `t` is `(observation_t, sent_action_t, reward_t, terminated_t, truncated_t)`, where `reward_t` results from applying `sent_action_t`. When an integration only learns the reward on the next loop, it calls `run.complete_transition(reward, terminated, truncated)`, which fills the previous row; the logger keeps one pending row for this. Validation: only the last row may have `terminated` or `truncated`; not both; they must agree with `termination_reason`; an RL-ready run has every `reward_valid` true. Zero-frame runs are discarded, never committed.

**Standard targets the reader exposes** (each with its mask):
- DAgger label: `expert_action` where `expert_valid`.
- Expert residual: `expert_action - base_action` where both valid.
- Executed residual: `sent_action - base_action` where `base_valid`; the default clean mask also requires `not safety_modified`.

v0 cannot separate the arbitration output from a safety-filter correction, and does not model actuator execution error.

## Predictions table (optional): `dataop/runs/<run_id>/predictions.parquet`

`inference_id`, `obs_frame_index`, `infer_start_ns`, `infer_end_ns`, `action_chunk[horizon, n]`, `valid_len`. Recommended for chunked policies, off by default to save space. Rules: `inference_id` unique within a run; a tick with `inference_id = -1` has `base_valid = False`; `0 <= chunk_offset < valid_len`; chunk shape matches the action schema. With temporal ensembling, v0 stores only the final selected `base_action`, and prediction provenance is diagnostic, not exactly reconstructible.

## Per-run manifest: `dataop/runs/<run_id>/manifest.json`

- `schema_version`, `run_id`, `status` (`staged` or `committed`), `episode_index`, `length`
- `fingerprint`: SHA-256 over a canonical byte serialization of schema version, action schema id, task (UTF-8), length, and `sent_action` as little-endian contiguous float32. Remapping evidence only: a remap requires a unique match and refuses ambiguous ones. `run_id` is the durable identity, and `dataset_id`/`revision` are stored separately
- `task`, `started_at`/`ended_at` (wall clock, for humans only)
- `termination_reason`: `success`, `failure`, `timeout`, `operator_abort`, `system_error`; `task_success`: bool or null; `labels`: list of namespaced strings (`failure:dropped`, `safety:collision`)
- `events`: typed list `{event_id, ns, frame_index, kind, source, reason, text}` for takeover requests, handbacks, drops
- `subgoals`: derived summary of the task's steps from `subgoal` events, `{name, start_frame, end_frame, status, reason}` with `end_frame` exclusive and status `completed`, `failed` or `unfinished`
- `failure_mode`: free-text name for how the run failed (`dropped_after_lift`, `no_grasp`), or null; groups failures across runs
- `takeovers`: derived summary of half-open ranges `[start_frame, end_frame)` per `control_mode` and `expert_source`
- `policy`: family, hub repo and revision or artifact sha256, code revision, config digest, chunk size, temporal ensembling, device and precision; null when no policy ran (a teleop demo, `log.run(policy=None)`, and then no frame may carry a `base_action`); `unknown` when the caller or an import did not say (the default). Before L2 the importer wrote null for an unrecorded policy, so a null `policy` in a manifest without a `task_rev` key reads as `unknown` (`schema.manifest_fields`)
- `task_id` (non-empty string) and `task_rev` (int >= 0): the Aftershock task and its revision, or `unknown`
- `planner`: `{name, id}` of the planner that picked subtasks, null when no planner ran, or `unknown` when not recorded. A changed planner gets a new id
- `env`: typed `robot_id`, `calibration_digest`, `operator` (pseudonym), `software` (lerobot and aftershock-logger versions), plus free-form `extras` (lighting, etc.)
- `action_schema` as above, `clock`: monotonic source description

`dataop/index.jsonl` is a derived cache rebuilt from manifests.

**Drive session fields (logger task L9).** A run recorded in a Drive session (below) also has `session_id`, `episode_in_session` (1, 2, 3 in the session), `session_frame_start` and `session_frame_end` (its half-open range of session frames, `end - start == length`), `go_ref` (the station owner's go for the session, `{by, at, scope}`, as the session record has it) and `rescue_outcome` (`success`, `failure` or `unknown` after a takeover, null when there was none). The five session fields come together. A run outside a session has none of these keys: the session fields read as null (not in a session), and `rescue_outcome` reads as `unknown` (not recorded). `validate` checks them (`schema.session_manifest_problems`). A run that stopped by Stop has the label `stopped`.

## Review layer: `dataop/runs/<run_id>/review.json`

Mutable and separate from the manifest and its digests. Written in review format 2, the format the logger shares with the Aftershock cloud (`review_format.py`), so a review moves between them without changing a byte.

- **File.** `{review_format: 2, run_id, rev, seq, reviewed, reviewed_at, reviewed_by, edits[], history[], locked, lock_log[], legacy_subtask_map}`. The text is `json.dumps(review, indent=1, sort_keys=True)` plus a newline, ASCII, every key written (nulls included), so loading and writing gives the same bytes; the review digest is the sha256 of that text. Reading is fail closed: a key, kind, source or value the format would not write refuses the whole file. No text anywhere holds a lone surrogate (a code point from U+D800 to U+DFFF outside a valid pair), `by`, `reason` and a step's `what` included: the reader, the writer and every operation refuse one, even an operation that would change nothing.
- **Edits.** `{edit_id, kind, payload, source (human|agent|check|splitter), by, job_id, agent_version, reason, status (proposed|accepted|rejected), created_at, decided_at, decided_by, accepted_seq, corrects, replaces, replaced_by, retracted_at, retracted_by, adjusted, legacy_reading, legacy_reading_history}`. Every source except `human` names its `job_id` and `agent_version`, and a new proposal from one of them gives a reason. `job_id` and `agent_version` are `unknown` only together, only on agent edits migrated from format 1 (which never recorded them), and only in a review with a `legacy_subtask_map`; a caller cannot pass `unknown`. `retracted_at` and `retracted_by` say when and by whom a person took back an accepted edit; they are set together, only on a rejected edit that keeps its `accepted_seq` and has no `replaced_by`, and are null otherwise. Kinds and payloads are listed in `review.py`: `outcome`, `failure_start`, `failure_type`, `exclude`, `segments` (subtask segments by subtask id), `step_boundary`, `segment_edge`, `drive_boundary` (recorded steps and drive spans by index), `reject_run`, `note`, `event_note`, `label`, `reading` (what a label means for training, `keep` or `exclude`), `name`, and the three split edits of a Drive session's review (below): `episode_boundary` `{at, to}` (moves the boundary at session frame `at` to `to`; `to` equal to `at` confirms it), `episode_merge` `{start, end}` (merges the episode that starts at `start` with the one that ends at `end`, and everything between) and `episode_split` `{at}` (splits the episode holding session frame `at` in two). Only a session review holds the split edits, a run's review never does (`check_against_manifest` refuses them), and format 1 has none of them.
- **Operations.** Every operation names the `rev` it read, is refused on a stale `rev` (the viewer API answers 409) or a locked review, bumps `rev` by one when it changes anything, and is recorded as one undoable step `{step_id, at, t, what, changes: [{edit_id, before, after}], undone, undone_at}` (at most 200 steps and 2 MB; the oldest go first). A person's edit is accepted at once. An agent, check or splitter edit waits as a proposal and never changes another edit; a person accepts it, rejects it, or corrects it (a person's edit with `corrects`, which rejects the proposal in the same step). An accepted edit is changed with `replace` or taken back: undo of its step, or, in the viewer, taking it back (`retract`: kept as rejected with its `accepted_seq` and its acceptance's `decided_at` and `decided_by`, with `retracted_at` and `retracted_by` set, so the edit accepted before it in the same slot is in effect again; the take back is its own history step whose `what` is always `take back`, whatever the viewer calls the action, such as "delete label"; the viewer's name for it is shown only for that action and not stored). A taken back edit cannot be accepted, rejected, replaced or taken back again, and `retract` refuses `unknown` as who or when. Outside a migrated review a take back always names who did it: a rejected edit with an `accepted_seq`, no `replaced_by` and no `retracted_at` (format 1's take back) is refused, in the edits and in history snapshots. Undo restores every edit a step touched only if each is still as the step left it and no other edit refers to one it would take away. Signing a run off sets `reviewed`; any later change to the edits clears it. Every result is checked against the recorded run before it is saved: frames inside the run, recorded step indices that exist, step names that match.
- **In effect.** In the one-value kinds the accepted edit with the highest `accepted_seq` is in effect; `exclude`, `note` and `label` all apply. A label's reading in effect is its latest accepted `reading` edit, or its format 1 reading. A reading applies only while its label is accepted: once the label is replaced or taken back, its readings stay with it and no longer apply, so no operation makes such a reading accepted: `accept` and `decide_many` refuse a proposed reading of such a label (nothing in a bulk decision is accepted then), `replace` refuses a new reading of it, and `undo` refuses (and `undoable` leaves out) a step whose undo would make such a reading accepted again; and the viewer shows each proposed reading with its label's text and span and offers no Accept for an obsolete one. `train_mask` is False for rejected runs, excluded spans, labels whose reading in effect is `exclude`, and on failed runs `[failure_start, next expert/blend frame)`.
- **Segments without an Aftershock task.** A segment names a subtask id, and the logger has no task to take ids from, so it never makes one up. A segment a person or agent names (from the dataset's lists) is stored as `unresolved` with its name in `legacy_name`, the same way a migrated name that matched nothing is stored, and keeps that name everywhere the logger shows or exports it. In a review migrated from format 1, a name already in `legacy_subtask_map` keeps the id the map gives it, and a new name is added to the map as `unresolved`. Mapping names to subtask ids is done in Aftershock.
- **Files from before the take back fields.** The logger at 4f4395e wrote format 2 edits without `retracted_at` and `retracted_by`. Both readers (`load_review`, and `read`, which `review.load` uses for every run) upgrade such a file in memory: an edit with neither key was not taken back and reads with both null, except a take back that logger made (rejected, `accepted_seq`, no `replaced_by`) in a review not migrated from format 1, which reads with both `unknown` (its history step may name the person, but the upgrade does not use it). `unknown` appears only in both fields together, only there, and never in a migrated review, where such an edit reads with both null as format 1 recorded it. An edit with only one of the two keys is refused. The file stays as it is on disk until the next change, which writes both keys. The review digest is that of the upgraded text, so for a file with any edit or history it differs from the sha256 of the bytes on disk. Batch lock digests are of the effective view, which taken back edits are not part of, so batches locked by that logger still verify.
- **Format 1.** Files from earlier versions (`{version: 1, ...}`, edit `id`, sources `agent` and `human`, readings stored on the label as `interpretation`) are read through a lossless migration and stay on disk as they are until their next change, which writes format 2 (or `aftershock-logger migrate-reviews`, which counts a review file that cannot be looked up or read (a broken link included), is not valid JSON or is in no known format as refused, names it, and exits nonzero, in `--dry-run` too). The migration maps recorded step names and segment names to subtask ids only by name, against a task when one is given, ignoring case and surrounding spaces, never by position; a name that matches nothing, or every name without a task, is `unresolved` and keeps its name and frames. `legacy_subtask_map` records the mapping. Agent edits from format 1 get `job_id` and `agent_version` `unknown`. `to_format1` turns a migrated review back into the exact format 1 file (it refuses a take back with `retracted_by`, which format 1 cannot say), and `effective()` of a migrated review equals what format 1 gave, so batch lock digests still match. Anything format 1 never wrote is refused, not dropped.
- **Synced from Aftershock (L7).** A station that uploads a dataset's runs pulls each run's review back from the cloud, where review lives, and writes it into `review.json` as the cloud stores it (the canonical text, so its digest is the cloud's, with its `rev` and its `locked` state). Before it writes any review it writes `dataop/sync.json` (`{sync_format: 1, source: "aftershock", workspace_id, station_id, since}`, no key or secret), which marks the dataset as synced. Offline edit reconciliation is not specified in v1, so a synced dataset is read only here: `review.transaction`, which every review change goes through (edits, decisions, undo, sign off, `migrate-reviews`), refuses every change, and the viewer refuses every request but listing and switching datasets and shows the dataset as synced. Reading, exporting and recording are unchanged. A marker that exists but cannot be read or is not in this shape counts as synced (fail closed). The syncing writer holds `dataop/batches.lock` shared, then the run's `review.lock` exclusive (the order `review.transaction` uses), writes a temp file in the run folder named `.review.json.*.tmp`, syncs it, renames it over `review.json` and syncs the folder, so a reader always sees a whole file and no logger change slips in between; a local review that changed since the station's last sync (or since its upload) is left as it is until a person decides. `sync.py` has the details.

## API

The logger owns ordering so it cannot drift:

```python
from aftershock_logger import RunLogger

log = RunLogger(dataset, action_schema=schema)          # one writer per dataset root, lock enforced
with log.run(task="pick up the tube", policy=policy_info, env=env) as run:
    for each tick:
        run.add_frame(frame,                              # calls dataset.add_frame(frame) first
                      sent_action=a_sent, base_action=a_base, expert_action=a_exp,
                      control_mode="base", expert_source=None,
                      obs_ns=t_obs, sent_ns=t_sent, inference_id=k, chunk_offset=j)
                      # optional RL fields:
                      reward=r, reward_valid=True, terminated=False, truncated=False)
    run.end(termination_reason="success")                 # stages the run
# leaving the block after run.end(): dataset.save_episode(), then commit
```

**State machine:** `active -> staged -> committed`, with terminal `discarded`, `save_failed` and `quarantined` (a staged run repair could not match, or a run stopped through the frame queue). `run.end()` sets the final tick's flag from the reason (`success`/`failure` -> `terminated`; `timeout`/`operator_abort`/`system_error` -> `truncated`) and rejects a contradicting flag. Any exception from `dataset.add_frame` discards the run and resets the LeRobot buffer. If `save_episode` raises, the staged run stays in `runs/` with a `save_error` note for `validate --repair`, and the logger refuses further runs. An exception before `run.end()` clears the LeRobot episode buffer and discards the sidecar state without saving. Leaving the block without `run.end()` is an error, never treated as success. A second `end` or an `add_frame` after `end` raises.

**What is verified when:** before save, the frame counter, buffer size, action shapes, sidecar indices, and byte equality of each `sent_action` against the logger's own copy of the frame actions; after save, that `save_episode` completed and the writer's episode index and length; at `finalize()` or `validate`, disk-level metadata, parquet rows and action equality. Supported LeRobot versions are listed in the README and tested in CI.

- `run.discard()` clears both the LeRobot episode buffer and the staged run (re-record).
- Crash recovery with `validate --repair` is non-destructive: an exact unique fingerprint match is committed; no match or several matches move the run to `dataop/quarantine/<run_id>/` and are reported; deletion only with `--delete-unmatched`.
- Crash points: before stage, nothing written; after stage and before or during save, a staged run with no matching episode goes to quarantine; after save and before commit, the staged run matches and is committed; after commit and before the index rebuild, the index is rebuilt from manifests.
- `run.event(kind, source, reason, text)` adds a typed event. `run.subgoal(name, status, reason)` adds a `subgoal` event (`started`, `completed` or `failed`); a step with no `started` begins where the previous one ended. `run.end(..., failure_mode=...)` names the failure. `run.predictions(inference_id, chunk, ...)` logs a chunk.
- Local filesystem only in v0; temp files in the destination directory, fsync, then rename. Remote URIs raise.

### Bounded write queue, controlled stop and quarantine (logger task L5)

A control loop must never wait for the disk, and must never move a robot it cannot record. `run.queue()` puts a bounded queue between the loop and LeRobot:

```python
with log.run(task=..., policy=...) as run:
    q = run.queue()                     # capacity: 2 s of frames at the schema's rate (max_seconds, or max_frames);
                                        # stall_timeout and stop_timeout (10 s each) bound the waits
    for each tick:
        q.put(frame, sent_action=..., ...)   # same arguments as run.add_frame; returns at once
    run.end(termination_reason="success")    # waits for every queued frame to be written, then stages
```

- `put()` checks the frame on the caller's thread (the same rules as `add_frame`; a bad frame raises `ValueError` and nothing is accepted), copies its values (arrays, lists and dicts; tensors are copied to the CPU, since the caller may reuse them) and returns. One writer thread hands frames to `dataset.add_frame` in order. While a queue is attached, `run.add_frame` raises, so frames have one path.
- At most `capacity` frames wait. The frame that finds the queue full is still accepted, so the queue holds at most `capacity + 1` frames and memory stays bounded however slow the disk is. After a write failure, the first `put()` (whose action already reached the robot) is also accepted before it raises; once the caller has been told of the stop by `put()`, `check()` or `run.end()`, `put()` accepts nothing more.
- **Controlled stop.** When the queue is full, or `dataset.add_frame` raises in the writer (a full disk, an encoder error), `put()` raises `ControlledStop` (a `RunError`) with `reason` `queue_full` or `write_failed` and a `detail`. `queue.check()` raises it without putting a frame, and `run.end()` raises it if a write failed or the writer is hung: no frame finished within `stall_timeout` seconds (10 s by default). A slow writer that keeps finishing frames is not hung, however long the drain takes. The caller holds the robot inside the run block (an `except ControlledStop` around the loop and `run.end()`, which holds the robot and re-raises), then leaves the block. Leaving the block starts the quarantine below, which can wait `stop_timeout` seconds for the writer and then writes to disk, so a handler outside the block is too late to hold the robot; it is the place to read where the frames went.
- **Quarantine.** When the block exits after a stop (by the `ControlledStop`, by another exception, or normally), the logger waits for the writer (at most `stop_timeout` seconds, 10 s by default, and not at all when `run.end()` already found it hung), resets the LeRobot episode buffer, and writes every accepted frame to `dataop/quarantine/<run_id>/`: `ticks.parquet` (the sidecar rows, frames that reached LeRobot first, then the queued ones, in frame order), `frames.parquet` (each frame's numeric low-dimensional values such as `observation.state`), `predictions.parquet` when logged, `manifest.json` with `status: "quarantined"`, `termination_reason: "system_error"`, checksums and a `quarantine` record (`reason`, `detail`, `frames`, `frames_written_to_lerobot`, `frames_queued`, `queue_capacity`, `dropped_features`, `lerobot_buffer_reset`), and `QUARANTINED.txt`. Image and video features are not kept and are named in `dropped_features`. The files go to a hidden temporary folder that is renamed into place only when complete. The run's state is `quarantined`; it is never committed and never becomes a LeRobot episode. The block then raises the `ControlledStop`, with `frames` and `quarantine_path` set, and its message says where the frames are (or a warning carries it when another exception is raised). The rename is the commit point: if only the folder sync after it fails, the record stands and a warning says so. When a retry finds a folder already at the destination, it accepts it only if it passes the partial run checks of `validate` (every file present and matching its recorded digest) and its digests equal those of the frames the run still holds; otherwise the retry raises, the frames stay in memory, and closing the `RunLogger` spills them.
- **No silent loss when the quarantine cannot be written.** If writing the quarantine fails (for example the disk is still full, or an interrupt arrives), the `ControlledStop` carries `quarantine_error` and its message says the frames were NOT written. The frames stay in memory, the logger refuses new runs, and `run.retry_quarantine()` writes them once there is space and lets the logger record again. `RunLogger.close()` (also on leaving its `with` block) retries every such run once, then writes it to `spill_dir`, and raises a `RunError` naming where the frames were spilled, or saying they were not written anywhere. A spill also updates the run's `ControlledStop` (`spilled`, `quarantine_path` and its message). When a `ControlledStop` is leaving the `RunLogger` block, the close error does not replace it: it is attached as `close_error` (and added to the stop's message), a warning repeats it, and the stop keeps propagating, so an `except ControlledStop` outside the block still fires. A plain `close()` raises the `RunError`. `spill_dir` defaults to a persistent per-user folder (`$XDG_DATA_HOME/aftershock-logger/spill`, else `~/.local/share/aftershock-logger/spill`), never the system temp folder, which is often cleared on reboot. That default is usually on the same disk as the dataset, so on a robot set `spill_dir` to a persistent folder on a different disk; the message says so when the default was used.
- **A stuck writer.** If LeRobot does not return within `stop_timeout` (or `run.end()` found the writer hung), the frame it holds is written to quarantine as queued, its late result is ignored, the LeRobot buffer is left alone (`lerobot_buffer_reset: false`), and the logger refuses new runs until the dataset writer is reopened. Because that thread can still change the dataset's files, `RunLogger.close()` keeps the dataset's writer lock until it returns (a background thread releases the lock then, or the lock goes when the process ends), so no second writer can open the dataset meanwhile; `close()` raises a `RunError` that says so.
- `run.discard()` on a queued run stops the writer first. After a stop it raises instead: stopped frames are quarantined, never discarded.
- **`validate` and `validate --repair`.** `validate` checks each quarantined partial run against its checksums, frame counts and fingerprint; problems, hidden `.<run_id>.*.tmp` folders left by an unfinished quarantine write, and quarantine folders whose `manifest.json` is missing or not valid JSON are errors (other hidden files are ignored); a sound partial run is a warning. `validate --repair` reports each quarantined partial run (kept, or left untouched with its problems), and each quarantine folder it cannot read as left untouched, and never commits, moves or deletes them.

### Live tap (logger task L10)

A station process on the same computer can watch the run being recorded. `RunLogger(..., live=True)` turns on the live tap (default off; with it off nothing below happens and `dataop/live/` is never made). Module `live.py`.

- **The caller's thread** only publishes an in-memory snapshot and appends transition records to an in-memory queue. Per frame that is one new snapshot (frame, mode, prompt, subtask, an owned copy of `observation.state`, each camera's time) published by one assignment, so a status always shows one frame's values, a bounds test on `sent_action` when the action schema declares bounds, and, only while a preview frame is due, one copy of that camera's image. No file I/O and no encoding. Every hook catches its own errors and never warns or writes; a tap error never reaches `add_frame`, `put`, `run.end` or the run block.
- **A daemon tap thread** writes every file, every 0.5 s and at once on a transition. On Linux it lowers its own priority; elsewhere it keeps the default. `close()` writes the last status and waits for the thread for at most 2 s. If the thread is still busy then, the writer lock is kept until it exits (a background thread releases it), so no newer writer's live files can be written over; `close()` raises nothing for this.
- **`dataop/live/status.json`** (`live_format: 1`), replaced by a temp file and a rename, so a reader always sees whole JSON. It carries `seq` (goes up with each write, also across writers on the same root), `pid` (the writer's process), `at_ns` (`time.monotonic_ns()`), `at` (UTC wall clock), `closed` (true in the last status a closing logger writes), `last_event_seq`, `run` (the run in progress or null: `run_id`, `task`, `task_id`, `task_rev`, `policy`, `planner`, `episode_index`, `started_at`, `elapsed_s`, `frames`, `frame`, `control_mode`, `expert_source`, `prompt`, `subtask_cmd`, `state` (`active` or `staged`), `termination_reason`, `task_success`, and `rec`: REC-04 gaps, frames missed and cameras with an open gap, and REC-05 flagged frames, spans and whether one is open), `last_run` (the last run that reached a final state: `committed`, `discarded`, `quarantined` or `save_failed`, with its termination and `rec`), `joint_state` (`{key: "observation.state", names, values}` from the dataset's feature names, only while a run is open), `action_schema` (`id`, `names`, `units`, `space`, `rate_hz`), `cameras` (per camera its image key, `width`, `height`, `last_ns` and `frame`), `queue` (`depth`, `capacity`, `max_depth` of the run's bounded queue, or null), `controlled_stop` (`run_id`, `reason`, `detail`, `frames`, `phase` (`detected` when the caller is first told, then `quarantined`, `not_written` or `spilled`), `quarantine` as a path relative to the dataset root or null, `quarantine_written`, `at`) and `preview` (`active`, `interval_s`, and per camera the file, frame, `obs_ns`, `at` and size of the last preview).
- **`dataop/live/events.jsonl`**, one JSON record per line with a `seq` that goes up by one, also across writers: a new writer continues after the last whole record it finds. Kinds: `run_start`; `control_mode` (`frame`, `control_mode`, `expert_source`, `previous`, `obs_ns`; every change, so a takeover of a few frames gives two records); `run_end` (`frames`, `termination_reason`, `task_success`, `failure_mode`, `ended_at`; at `run.end()`, or with the final state for a run that never reached it); `run_state` (the final state); `controlled_stop` (once when detected, again each time its frames' place is known: after the quarantine write, a retry or a spill); `rec_result` (`check_id`, `result: warn`, `state` `open` or `closed`, `frames` as `[start, end)` with `end` null while open, a `message`, and for REC-04 the `camera`, `seconds` and `review` (longer than 1 s)); and `dropped` (records lost because the tap fell more than 10,000 records behind). Each record has `at`. The file holds at most 10,000 records: then it is renamed to `events.1.jsonl` (replacing the older one) and the new file starts with `{"kind": "file_start", "first_seq": n}`. So disk use is bounded to two files.
- **Record checks while recording.** REC-05: a frame whose `sent_action` is outside the action schema's declared bounds opens a span, and the next frame inside closes it (no bounds, no REC-05 here; the station or the cloud applies the robot profile's limits). REC-04: needs `camera_ns={camera: capture time}` passed to `add_frame` or `put` (keys are camera names, the image key after `observation.images.`, or the full key). A camera whose capture time has not moved for more than 1.5 frame periods opens a gap at the first frame it missed; its next new frame closes it with the seconds missed. Without `camera_ns` each camera's time is the frame's `obs_ns` and no gap is reported. `camera_ns` and these results are live only: they are not written to the sidecar.
- **Preview only on request.** While `dataop/live/preview.want` exists and its mtime is under 10 s old, the tap keeps one frame per camera every `interval_s` seconds (read from the file's JSON body `{"interval_s": n}`, at least 1, default 2): the caller's thread copies the image when one is due, and the tap thread scales it to at most 320 px wide and writes `dataop/live/preview/<camera>.jpg` (JPEG quality 70, with Pillow) by temp file and rename. When the request is gone or older than 10 s, copying stops and the preview files are deleted on the tap's next round (within 0.5 s). Without a request no image is copied or encoded.
- **Failure.** Any tap error (a read only folder, a full disk, a missing encoder) is caught, warned once (`RuntimeWarning`, from the tap thread, never raised further), written to `dataop/live/error.json` when possible, and turns the tap off for the rest of the run: no more status, events or previews until the next run starts, when it tries again and deletes `error.json` after its first good status. The recorded run is the same byte for byte with the tap on, off or failed.
- **Crash safety.** Files are not fsynced: they describe the present and are rewritten within a second. A process that dies mid-write leaves the previous whole `status.json` (and a hidden temp file the next writer removes) and at worst a torn last line in `events.jsonl`, which readers skip and the next writer cuts off before appending. A reader judges freshness from `at_ns` or `at`, `pid` and `closed`.
- **Privacy.** Every string written, dictionary keys included, is cleaned of the dataset root (`<root>`), the home folder (`<home>`) and the host name (`<host>`). Camera ids in status keys and preview file names are the cleaned camera names, made unique. No key or environment value is read or written.
- **Readers.** `live.read_status(root)`, `live.read_error(root)` and `live.read_events(root, after_seq)`, which returns the records after `after_seq` in order from both files (read again when a rotation happened during the reads, each seq once), with `{"kind": "gap", "from_seq", "to_seq"}` wherever records were rotated away, or `[{"kind": "reset", "last_seq"}]` when the files hold no seq that high.
- **Not part of the dataset.** `dataop/live/` is not in the sidecar or the dataset: `validate`, `import` and `export` ignore it, and an uploader must not send it as a run file.

### Drive sessions (logger task L9)

In Aftershock's Drive mode the station runs the customer's model as one continuous session from Start to Stop and splits it into episodes. `SessionLogger(run_logger, session_id=..., station_id=..., go=..., model_id=..., task=..., task_id=..., task_rev=..., policy=...)` records one session on a RunLogger's dataset (module `session.py`). The logger records what the station's session runner decides; it does not run the state machine.

- **Session frames.** Every tick goes through `sess.add_frame(...)` (the arguments of `run.add_frame`), which writes it to the open episode's run or to the active gap and returns its session frame: its address `(session_id, session_frame)`, counted from 0 at Start and never reset. Every session frame is in exactly one run or one gap.
- **Files.** `dataop/sessions/<session_id>/session.json` (the session record), `evidence.parquet` (the evidence log), `review.json` (the session's review, format 2 with `rev`, keyed by the session id; it starts empty at rev 0 and the splitter's proposals and people's split edits go there) and `gaps/` (the gap dataset). A session id is never reused.
- **Session record.** `{session_id, station_id, go, model_id, planner (null: no planner in this version, so the RunLogger must be built with planner=None), task_id, task_rev, fps, started_at, ended_at, ended_by (user_stop or fault_stop), fault, session_frames, runs[], gaps[]}`. `runs[]`: `{run_id, episode_in_session, range {start, end}, write_status (pending, committed, failed), termination, rescue_outcome, stopped}`. `gaps[]`: `{gap_id, range, gap_episode_index, moved_by (person, reset_skill, task, none, unknown), reset_checks {home, zone, expert_active, torque, cameras} (null where a check did not run), short_stop (a range or null)}`. Times are UTC ending in `Z`. It is rewritten (temp file and rename) at every boundary: a gap closing, a seal, a write result, the end.
- **Gaps.** The ticks between episodes (the reset, the time a sealed run is being written, the time after Stop) are a gap. Each gap is one episode of a LeRobot dataset at `sessions/<session_id>/gaps/`, made with the runs' features (every camera, `observation.state`, `action`), fps and video setting, with its own `dataop/` sidecar, so each gap has sidecar ticks and a manifest like any run. A gap's manifest has `session_gap` `{session_id, gap_id, session_frame_start, session_frame_end, short_stop, moved_by, reset_checks}`, no session fields, and `termination_reason` `unknown` with neither terminal flag on its last tick, because a gap is not an episode. The first gap opens at session frame 0, a gap opens on the first frame after a seal, and `start_episode` closes it on the reset handoff's tick with a `reset_pass` event. An empty gap is not written.
- **Episodes.** `sess.start_episode(moved_by=..., reset_checks=...)` closes the active gap and opens a run (with an `episode_start` event) that takes the next frame; it returns the Run for events, predictions and subgoals. `sess.rescue_success()` adds a `rescue_success` event (it seals nothing). `sess.seal_episode(termination_reason, rescue_outcome=...)` fixes the termination on the last recorded tick and adds an `episode_end` event. With a takeover, `rescue_outcome` is `success` or `failure` for Rescue done (termination `failure`) and `unknown` for a Stop (`operator_abort`) or a fault (`system_error`); a takeover episode cannot end as `success` or `timeout`. Without one it is null.
- **Short stop.** A Stop (`operator_abort`) that ends an episode of 1 s or less (`SHORT_STOP_S` times the dataset's fps frames, or fewer) saves no run: the run is discarded and its frames move to a new gap that starts at the episode's first frame, with `short_stop` set to their range. The session keeps an owned copy of an episode's first observations until it is longer than that, so a caller that reuses its buffers cannot change them. Each tick moves as the run recorded it (a reward added later by `complete_transition` included) with its terminal flags cleared, and the run's events move with their frames; its predictions table, if any, is not kept.
- **Write status.** A sealed run is staged and its write is `pending`; `sess.write_pending()` saves it to the dataset and commits it (`committed`). The status follows the commit: once the manifest is committed the run is `committed`, and a later step that fails (rebuilding the index) is only warned. A failed write moves the run's sidecar record (manifest and ticks) to `dataop/quarantine/<run_id>/` with its sealed termination, records a `persistence_error` row, and makes the session end as `fault_stop` with the fault `persistence_error` (unless a fault was named), even after a user's Stop. A failed save also stops the RunLogger (as before), so no further episode starts; recording goes on in the gap until the session ends. A new episode cannot start, and the session cannot end, while a write is pending.
- **Evidence log.** `evidence.parquet` has one row per record, `{session_frame int64, kind string, payload string}` with the payload a JSON object; `session.read_evidence` gives it with the payload as a dict. Kinds: `state` (from, to, event; `sess.state`), `criteria` (per frame in policy or expert), `reset_check` (per frame in reset_wait), `fault` (`sess.fault`), and `write` and `persistence_error`, which the session writes itself. It covers gap time as well as runs and is rewritten at every boundary.
- **Ending.** `sess.finalize(ended_by, fault=...)` refuses while an episode is open or a write is pending, closes the active gap, checks that every session frame is in exactly one run or gap, closes and finalizes the gap dataset, and only then writes the final record. If the gap dataset cannot be finalized it records `persistence_error` and raises; the session stays open, takes no more frames, and a second `finalize` call retries with the end decided the first time. Closing a session that was not finalized (`close()`, or leaving its `with` block) keeps every frame it recorded: an open episode is sealed as `system_error` with a `fault` row (`session_closed`) and written (a terminal flag on its last tick is cleared first, since a fault seals at any length), and the active gap is saved; the session stays on disk with `ended_at` null. An error there is raised as a SessionError, or warned when another exception is already leaving the block.
- **The session review.** `review.json` holds only the split edits (`episode_boundary`, `episode_merge`, `episode_split`), made by the splitter or a person with the format 2 operations; their frames are session frames. The split edits in effect apply one after another in acceptance order to the recorded timeline (each run an episode, each gap a gap): a boundary moves only between two segments that are not both gaps and leaves each at least one frame, a merge takes the episode that starts at `start` and a later one that ends at `end` and swallows everything between, gaps included, and a split leaves both parts at least one frame. Every episode an edit changes needs review and gets the id `session.episode_id_for(session_id, edit_id, start, end)`; one that again matches a committed run exactly takes the run's id. No edit may change the frames of a run whose write failed. `session.effective_timeline(record, review)` gives the result, the same rule as the Aftershock cloud's.
- **The go** is checked as the cloud takes it: `{by, at (UTC ending in Z), scope {model_id, planner (null), task_id, task_rev >= 1, station_rev >= 0}}`.
- **validate** checks every session folder: the record's keys and field types (times, the go, run and gap entries with exactly their keys, reset checks, `stopped` exactly for `operator_abort`), ranges and `episode_in_session` order; each failed run's quarantined manifest and ticks (whole by their digests, and frames 0 to n-1 of the run's range); each committed run's manifest against its entry (session fields, termination, rescue outcome, the `stopped` tag); the gap dataset with `validate` and each gap against its gap episode (range, length, `short_stop`, `moved_by`, `reset_checks`); for an ended session, coverage, no pending write and `fault_stop` after a failed write; the evidence rows (columns, kinds, frames inside the session, JSON object payloads) and `review.json` (`session.check_against_session`: keyed by the session id, only split edits, every frame inside the session, and for an ended session that covers every frame, the edits in effect apply). A committed run that names a session whose record does not list it is an error. An open session is a warning. A dataset with no `sessions/` folder has nothing to check, so older datasets are unchanged.

## CLI

- `aftershock-logger validate <root>`: episode binding, frame counts and indices, monotonic times, `sent_action == LeRobot action`, schema checks, takeover ranges, staged or orphaned runs. Nonzero exit on any error; `--json` report.
- `aftershock-logger inspect <root>`: runs, outcomes, minutes per control mode, takeovers.
- `aftershock-logger remap <old_root> <new_root>`: rebinds runs to a filtered or renumbered dataset by fingerprint.

## Python reader

`DataopDataset(root, missing="error" | "exclude" | "mask")`: a PyTorch dataset that joins LeRobot frames with sidecar fields by `(episode_index, frame_index)`, returns tensors plus validity masks and the standard targets above, and keeps LeRobot's delta-timestamp sampling. Default `missing="error"`. Original LeRobot episode and frame indices are preserved even when episodes are excluded. It exposes the bound episode ids and a validation summary. It does not rebalance, relabel, split or publish a dataset. An `export --into-lerobot` command that copies selected fields into a derived dataset is planned for v0.3.

## Batches, import and export (v0.4)

See `docs/DESIGN_batches_import_export.md` and `reviews/round17_decisions.md`. In short: each batch (a pack in
Aftershock) is one file, `dataop/batches/<batch_id>.json`, holding its runs, its identity (station, task, policy,
planner) and `mixed_policy`; all batch files change under one lock (collecting, reviewing, locked; locked runs refuse
review edits, and a locked batch's membership is frozen until it is unlocked with a reason). A dataset written before
logger task L3 keeps one `dataop/batches.json`; it reads the same, and the first change moves it to per-batch files.
Import binds runs to an existing LeRobot v3.0 dataset; control mode and outcome may be `unknown` and timestamps
`from_dataset_timestamp` for imported runs, and a known base action may have no inference record. Export writes a new
LeRobot dataset from locked batches with the `filtered`, `dagger` or `residual` recipe and records its provenance in
`dataop_export.json`.

## Task, planner and prompt fields (logger task L2)

The prototype added subtasks and a planner (a layer above the VLA that picks the next subtask during a run). The manifest records `task_id`, `task_rev` and `planner`, and every tick records `prompt`, `prompt_rev`, `subtask_cmd` and `control_gen` (tables above). With these, a planner's commands become first-pass subtask labels in Review, failure analysis can tell a planner mistake from a VLA mistake, and training gets subtask prompts.

Three cases stay apart in every one of these fields: a value; null, known to be none (no planner ran); and `unknown`, the value existed but was not recorded. A field the caller does not pass is `unknown`, never guessed, and a field an older logger never wrote reads as `unknown`. Import writes `unknown` for all of them, and for control mode and outcome when the mapping has no source. A null policy or planner needs an explicit `"policy": null` or `"planner": null` in the mapping; no preset sets them, since auto-detection picks `demos` whenever nothing says a policy drove, which is not evidence that none ran; an episode whose mapping says no policy ran but whose frames the policy drove is skipped with the reason. A mapping can also give the planner as `{name, id}`.

API: `RunLogger(..., planner=PlannerInfo(name, id) | None | "unknown")` sets the planner for every run, `log.run(..., policy=, task_id=, task_rev=, planner=)` sets the policy and task and may override the planner, and `run.add_frame(..., prompt=, prompt_rev=, subtask_cmd=, control_gen=)` records the per-tick fields. `add_frame` refuses a bad value, a counter that goes down, a changed prompt with the same `prompt_rev`, a `subtask_cmd` or a changing prompt in a run whose planner is null, and a `base_action` in a run whose policy is null, before the frame reaches LeRobot. The reader exposes the tick fields as `dataop.prompt`, `dataop.prompt_rev`, `dataop.subtask_cmd` and `dataop.control_gen`.

## Non-goals for v0

Uploading, cloud storage, multiple concurrent writers, real-time takeover control, and curation or materialization of derived training datasets. Those belong to the hosted Aftershock product.
